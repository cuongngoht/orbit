# Orbit 0.5.0 — Proactive skill and agent orchestration: design

**Status:** proposed with the 0.5.0 backlog. Nothing here changes runtime behaviour yet.
**Drafted:** 2026-11-05, on `release/0.5.0` at `f96beed` (plugin 0.4.0).
**Backlog items:** [B21, B22 and B23](0.5.0.md); B5's router work is folded into B22.
**Decision:** [ADR 0050](../adr/0050-the-host-activates-orbit-by-capability-and-orbit-verifies-what-happened.md).
**Proof:** [the activation benchmark](0.5.0-activation-benchmark.md).

The product principle this design serves: **Orbit is not a mandatory workflow.** It is a capability layer that Claude
Code uses by itself: the right skill, agent and verification at the right time, and nothing when nothing helps.

## 1. The question

Can a developer install Orbit and use Claude Code normally, while Claude discovers and invokes the right Orbit skills
and subagents, composes them when needed, avoids unnecessary delegation, and produces independently verified outcomes?

**Today, no.** Three findings settle it.

1. **Claude Code picks a skill from its description, and Orbit's descriptions do not fit.**
   - The skills listing has a budget: 1 % of the context window, at most 1,536 characters per entry. When the listing
     overflows, the descriptions of the least-used skills are dropped and only their names stay.
   - Orbit's 25 skill descriptions total 17,924 characters, mostly 600 to 1,017 each, and the words that say when to
     use a skill come last.
   - This session's own skills listing already shows `orbit:satellite` with no description.
   - The 20 agent descriptions add 12,180 characters to every session's Agent tool list.
2. **The router suggests the wrong things, and nothing decides how much Orbit to use.**
   - It classifies a prompt with 15 English keyword intents and shows one-cue (low-confidence) matches.
   - It appends "Orbit coordinates a task by default" to every prompt it routes.
   - This design request was routed as `qa` with six wrong suggestions (`orbit-test-suite`, `orbit-test-plan`,
     `orbit-failure-analyst`, `orbit-ui-test`, `orbit-ui-map`, `orbit-requirements`) and a missing playwright.
   - Three background-task notifications, delivered to the hook as prompts, were routed `investigation (high
     confidence)` because a report inside them said "investigate" and "explore".
   - No module chooses between one specialist, a coordinated workflow and a Satellite mission. Every request that
     reaches `/orbit-help` with a change word becomes the full engineering workflow.
3. **Nothing measures it.**
   - Every 0.4.0 benchmark prompt names the skill and its commands (`benchmark/lib/source/brief.mjs:52-90`,
     `benchmark/lib/qa/round.mjs:16-22`).
   - There is no negative case and no "without Orbit" arm.
   - The stream parser keeps tool-name counts only (`benchmark/lib/core/host.mjs:24-43`).

What already exists is better than that answer suggests:

- **One registry** of every usable resource, with its states kept apart.
- **A deterministic resolver** that picks one provider per requirement by an ordered table.
- **A session trail** that records every routing decision and every Skill and Agent call, without the prompt's text.
- **A per-turn fold** that already says `followed · diverged · not-invoked`.
- **Three engines** that compose owners: automation, goal and Satellite.
- **Owner-verified evidence** throughout.

The gap is the last mile into the host, and a way to prove it.

## 2. What Claude Code lets a plugin do

Verified against the Claude Code documentation and against the native hook payloads this repository already captured
(`test/fixtures/hooks/claude/*-2.1.309.json`, `*-2.1.314.json`). "In use" means Orbit relies on it in 0.4.0.

| Mechanism | What it can do | Status |
|---|---|---|
| Skill listing and `description` | The model reads every listed description and invokes the `Skill` tool. It is the only automatic trigger a plugin controls. The budget is 1 % of the context window, at most 1,536 characters per entry, and the least-used skills lose their description first. | In use; overflow observed in this session |
| `disable-model-invocation`, `user-invocable` | Either the person only, or the model only, may invoke the skill. A skill the model may not invoke costs no listing budget. | Documented; unused (every Orbit skill is both) |
| Plugin agents and their `description` | The model dispatches the `Agent` tool with `subagent_type: "orbit:<name>"`. "Use proactively" in a description encourages delegation. | In use (`PreToolUse-Agent-2.1.309.json`) |
| Agent `tools:` | An allowlist the host enforces, which is the profile. A plugin agent's `permissionMode`, `hooks` and `mcpServers` are ignored. | In use (Satellite profiles) |
| Agent `skills:` | Preloads a skill's full content into the subagent. | Documented; unused |
| `UserPromptSubmit` → `additionalContext` | Text beside the prompt. It can also block a prompt. | In use (the router) |
| `SessionStart` → `additionalContext` | Text at start, on `resume`, on `clear` and after `compact` (`source`). | In use (lessons, memory lines) |
| `PreToolUse` → `permissionDecision: deny` | Refuses a call. It can never force one. | In use (component switches) |
| `PostToolUse` → `additionalContext` | Text after a tool returns, including after an Agent returns. | Documented; Orbit's Claude adapter returns nothing today |
| `PostToolUseFailure` → `additionalContext` | Text after a failed call. | In use (`formatFailure`, `skills/orbit-learn/hosts/claude.mjs:36`) |
| `SubagentStart` → `additionalContext` | Text into the subagent's own context. | Documented; unused |
| `Stop` and `SubagentStop` → `decision: "block"` | Keeps the turn going with a `reason`. `stop_hook_active` guards a loop and is on both payloads (`Stop-2.1.309.json`, `SubagentStop-2.1.314.json`). | Documented; unused |
| Forcing a tool call | **Not possible.** No hook can make the model call Skill or Agent. | Documented |
| `claude -p` | Runs the plugin's hooks unless `--bare`. `stream-json` carries every `tool_use` block, and a subagent's calls carry `parent_tool_use_id`. | In use (the benchmark runner) |
| `claude plugin eval`, `/skill-doctor` | Trigger evals with a `tool_used: Skill` grader and a no-plugin baseline; listing cost per skill. | Documented; M0 uses them |

**The constraint that shapes everything:** no hook can make the model call a tool. So Orbit has two levers on
selection and three on follow-through.

- **Selection:**
  - the metadata the model reads, meaning the skill and agent descriptions;
  - the context a hook adds beside a prompt.
- **Follow-through:**
  - a hook that adds one line after an Agent returns or a command fails;
  - a Stop hook that may hold a turn open, boundedly, with a reason;
  - the engines' own `context` and `step` answers, which already say what is next.

Everything else is Orbit observing, after the fact, what happened, and verifying it on owners' records. The items still
to confirm on the runner's pinned Claude Code (2.1.314) are M0's ([§7](#m0--measure-and-confirm-no-product-code)).

### 3.3 Activation states, kept apart

The request asks that installed, enabled, runtime-ready, eligible, permission-approved, selected, invoked, and completed
and verified stay distinct. Orbit already holds each one in a different place. The 0.5.0 work adds a fold that reads
them in order ([§5.11](#511-the-activation-chain-and-independent-verification)).

| State | Where it is held | Who reads it |
|---|---|---|
| Installed | The plugin tree, a runtime receipt, an extension registration, a playbook's status | Each family's provider |
| Enabled | A component switch, an MCP or tool desired state, a playbook `active` | `resource().enabled` |
| Runtime-ready | The provider's check (a shipped skill is always ready; an agent is not on a protocol-2 host) | `resource().runtimeReady` |
| Eligible | available ∧ selection ≠ `disabled` ∧ policy leaves a use | `resource().eligible`, the resolver |
| Permission-approved | The policy verdict (`src/policy.mjs`), a protected boundary's approve-once in Control, the host's own permission mode | The resolver; `authorize()`; the host |
| Selected | By Orbit: `selected` or `approval` in the RouteDecision (a suggestion). By the model: a Skill or Agent tool use. | Trail `prompt.submitted`; trail `skill.invoked` and `agent.invoked` |
| Invoked | The call passed the switch (PreToolUse); the Agent call answered an `agentId`; `SubagentStart` | Trail `skill.invoked` (outcome ok), `agent.launched`, `agent.started` |
| Completed and verified | The owner's record: a task COMPLETED, an investigation's outcome, a frozen snapshot, an acceptance criterion verified, a mission VERIFIED. The work view says `verified` only from a completed linked task. | The owners' read commands; `workViewOf` |

### 3.6 Eligibility and activation gaps

- **Unreachable by the router.** Five skills: `orbit`, `orbit-reverse-engineer`, `orbit-security-audit`,
  `orbit-improve` and `satellite`. No intent, refinement or need asks for what they provide. The model can still find
  them through their descriptions, as long as those survive the listing.
- **Selected when they should not be.** Two agents: `orbit-map-healer` and `orbit-qa-case-writer` can be picked from a
  prompt's words, although each needs its parent's preceding step.
- **Shadowed.** Two direct agents, `orbit-engineering-agent` and `orbit-qa-agent`, are never picked by the router,
  because the resolver's family order puts the skill providing the same capability first. That is correct for a direct
  request, where the person sees the work in the session, and the coordinator dispatches them anyway.
- **No provider.** The `engineering` intent asks for `engineering.context`, which nothing provides. That intent always
  routes nowhere, although `node <engine>/cli/engineering.mjs recall` answers it.
- **Stale or missing names.** `orbit-architecture` names an agent that does not exist. `satellite` and
  `orbit-requirements` name their agents by pattern. `orbit-engineering-observer` and `orbit-architecture-scanner` are
  named by no skill.
- **Generated playbooks are never native skills**, by design. Their activation path is the coordinator (a `playbook`
  step) or `skill-factory.mjs show`. The router may suggest one by its `project:` key.
- **Protocol-2 hosts get skills only.** On Codex, Antigravity and Grok Build an agent is not runtime-ready.

## 4. Architecture gap analysis

| Module | What it does today | Reused as | Change for 0.5.0 | Rejected duplicate |
|---|---|---|---|---|
| `src/resources/` (Effective Resource Registry) | Five families, one isolated provider each, states kept apart | **The** discovery answer, unchanged | `routing.via` carried on agent rows | A second "skill index", or a per-host capability list |
| `catalog/components.json` | Routing data per skill and agent | The activation metadata | `via` on agent rows; an `engineering-memory` builtin; `orbit-release` signals fixed | A per-skill routing table in SKILL.md bodies; flags such as `proactive: true` |
| `src/routing/intents.mjs`, `classify.mjs`, `terms.mjs` | 15 English keyword intents, n-gram match, one-cue = low | The intent table | Vietnamese cues; `security` intent; reachability refinements; opt-out, continue and halt cues; cues in the prompt's head outrank a pasted tail; prompt-shape counts | A model call in the hook; embeddings |
| `src/routing/select.mjs`, `resolve.mjs`, `graph.mjs` | One provider per requirement; RouteDecision v2 | The resolver | A `via` agent is selectable only as its parent's transitive provider; RouteDecision v3 adds `strategy` and `activation` | A second resolver for agents |
| `src/routing/format.mjs`, `src/lifecycle/subscribers/router.mjs`, `cli/router-hook.mjs` | ≤ 2 KB of suggestions, plus an ADVICE line on every routed prompt | The prompt hook | Nothing for NONE; one strategy line; ADVICE only for COORDINATED; a host envelope answers nothing | A second prompt hook |
| *(new)* `src/routing/strategy.mjs` | — | — | One ordered table: NONE · DIRECT · COORDINATED · SATELLITE · RESUME | A "planner" that decomposes prompts |

## 5. The architecture

### 5.1 The flow

```
 person's prompt
   │
   ▼ UserPromptSubmit (cli/router-hook.mjs, fail-open, ≤ 5 s, no text kept)
 classify (intents, cues, shape) ─► Effective Resource Registry ─► resolver: one provider per requirement
   │                                                                  │
   └────────────► strategy table (src/routing/strategy.mjs) ◄─────────┘   + workflowOf, host row, open work
                  NONE · DIRECT · COORDINATED · SATELLITE · RESUME
   │
   ▼ ≤ 2 KB beside the prompt (nothing for NONE)        trail: prompt.submitted {strategy, activation}
 the host's model decides ─────────────────────────────────────────────────────────────────────────┐
   │ DIRECT: Skill orbit:<skill>, or Agent orbit:<agent>, or its own tools for a trivial edit        │
   │ COORDINATED: automation.mjs start (orbit-help) · orbit.mjs goal start (orbit)                   │ trail: skill.invoked,
   │ SATELLITE: satellite mission start      RESUME: automation | goal resume, track --continue      │ agent.invoked/launched
   ▼                                                                                                 │
 owners execute: tasks · workflows · goals · investigations · missions (journals, receipts) ◄────────┘
   │   PostToolUse(Agent orbit:*): one line, the owner record that settles it
   │   PostToolUseFailure(Orbit CLI): the owner's recovery row
   │   Stop: hold a governed workflow to its next ready step, at most twice per prompt
   ▼
 verification on owners' records ─► work view (verified) ─► activation fold: suggested → selected → dispatched → executed → verified
```

Three rules hold the whole way down:

- **The host decides, Orbit suggests, bounds and verifies.** A hook's text is a recommendation. Only an owner's record
  is evidence.
- **Selection is not execution, and execution is not verification.** Each is a separate link in the activation chain,
  with its own source.
- **Nothing new owns state.** Every new fact is either a table answer computed from what exists, or one allow-listed
  trace event.

### 5.2 Unified resource discovery

The Effective Resource Registry stays the only answer to "what can be used here", with its two readers (the router and
Orbit Control). When a component is installed, generated, enabled or disabled, the next read reflects it with no
per-component code: a shipped skill through the tree and `componentOn`, a playbook through the factory's status, a
server or tool through its state and receipts.

**One new catalog column: `via`.** An agent row may say `"via": ["<skill>", …]`, naming the shipped skills whose
playbook dispatches it. With no `via`, the main session may dispatch the agent directly. It has three readers:

- **The resolver.** A `via` agent is selectable only as a transitive provider pulled in by one of its `via` skills, so
  `orbit-map-healer` is never suggested straight from "the locator drifted".
- **The formatter.** A parent's line names the agents it dispatches.
- **A catalog test.** Every `via` names a shipped skill whose SKILL.md names the agent, and every agent a SKILL.md
  names is either direct or lists that skill. That test catches `orbit-context-scanner`.

No other column is added. `requiresSignal` already means "only when named", and every other fact (what an agent may
touch, what record proves its work) already has an owner: the `tools:` allowlist, `STEP_KINDS.domains`, and the work
view.

### 5.3 Intent understanding (B21, part 1)

**No new contract: the goal analysis is the structured reading.** `src/goal/` already reads a specification into:

- requirement rows of kind `explicit · derived · assumption · unknown · conflict · decision`, each with a `sourceRef`
  into the persisted spec (`spec@<digest>#L<n>`);
- acceptance rows with their verification;
- unknowns and conflicts;
- a structured intent: category, work kinds, capabilities, verification, dependencies, missing prerequisites
  (`src/goal/fields.mjs:7-34`).

That covers the distinctions the request lists: explicit requirements, inferred hypotheses (`derived`, `assumption`),
acceptance criteria, business decisions (`decision`), unknowns and verification expectations. Constraints are the one
missing kind. **Proposed additive change:** `constraint` joins `REQ_KINDS` (`src/goal/vocab.mjs:10`) for statements a
change must not violate, such as a public API kept or no new dependency.

The engine routes a request's reading by what the request is:

| The request | Where it is read | Provenance |
|---|---|---|
| A specification: several requirements, acceptance criteria, a pasted work item | The goal domain (`orbit.mjs goal start --stdin`), through COORDINATED with `how: goal` | The goal domain persists the spec; every row cites it by line |
| One objective that needs several owners | Automation, with the host's declared routing intent (`automation.mjs start --intent=<id>`): never classified again from keywords | The objective sentence, scrubbed and bounded, plus the request's digest |
| A named work item | The requirements domain; its snapshot is the authority | The source's own revision |
| One specialist's job | The specialist's own playbook | None needed |

Guesses never become accepted requirements. `assumption` and `derived` rows stay what they are, a requirement's
authority is derived (accepted or draft), and only a person's `--human` answer decides a question.

Vietnamese and English are the same reading. The model reads the goal into typed fields, so a Vietnamese goal and its
English twin plan the same; the goal domain already states this property. The keyword router gains Vietnamese cues only
so that its *suggestion* is right.

The prompt's text is never stored by a hook. The original request is preserved only where an owner already keeps one,
which is the goal spec. Otherwise it is kept by digest and length.

### 5.4 Contextual discovery, relevance and sufficiency (B21, parts 2 and 3)

**A `relevant` section joins the context package** (`src/context/relevance.mjs`, pure, composed in `cli/context.mjs`).

Candidates come from the owners that already hold evidence:

- architecture facts and their cited scopes;
- the system graph's nodes and the files they cite;
- intelligence integrations, with the code that shows each;
- knowledge claims, and engineering recall;
- the working set;
- `impact.mjs` reach and `obligations.mjs` required checks, once paths are known;
- **references the host proposes**, verified against the tracked tree (`git ls-files`, and a bounded identifier
  search within `MAX_EVIDENCE_FILES`).

A reference the tree does not hold is refused by name and never listed. Orbit never invents a file, a symbol or a
relationship, because every item carries the evidence that shows it.

```json
{ "kind": "file | symbol | component | check",
  "ref": "src/orders.mjs",
  "class": "direct | dependency | downstream | verification | unknown",
  "evidence": [{ "source": "architecture", "id": "af-…" }, { "source": "tree", "id": "tracked" }],
  "freshness": "current | stale | unknown",
  "by": "engine | host-verified" }
```

- **Class.** `direct` means named by the request or proposed and present. `dependency` means the item depends on a
  direct one, by a graph or integration fact. `downstream` means it depends on the change, by `impact.mjs` reach or a
  reverse graph edge. `verification` means a declared check or test that holds it, by `obligations.mjs` or the test's
  declared scope. `unknown` means present, with no relation evidence.
- **Freshness** comes from each fact's own scope fingerprint (`src/freshness.mjs`), never from HEAD.
- **Bounded:** at most 40 items, ordered by class and then evidence weight, with the rest counted.
- **"Semantic" without dependencies.** Identifier-split lexical matching (`createOrder` matches `create order`), plus
  the host's own proposals, which are verified. No embeddings, because zero dependencies is a rule. File-level import
  graphs belong to a language pack such as `orbit-dotnet`, never to `src/` (AGENTS.md: a technology is an adapter's to
  know).

**Sufficiency** is one word with its reason, by an ordered table:

| Word | When | Then |
|---|---|---|
| `ENOUGH` | Every required class is filled with current evidence, and no blocking unknown is left | Proceed |
| `DISCOVER` | A class is empty or stale, and a source can fill it | Targeted reads: the named targets, never a full scan (`architecture ensure`'s TARGETED decision) |
| `ASK` | A blocking unknown that no source can settle | One question through the existing question flow (`requirements ask`, or a goal's `missing`), answered only by a person |

That avoids clarification ceremonies: `ASK` is reached only when reading cannot settle the matter.

### 5.5 Proactive skill selection: the strategy table

A new leaf, `src/routing/strategy.mjs`, holds one ordered table. The first matching row wins and the last row always
matches, like `src/help/vocab.mjs` `ROUTES`. Its facts are handed in by the composition root (`cli/router-hook.mjs`):
the classification (intent, `matched`, cues, prompt shape counts), the RouteDecision, automation's own `workflowOf`
answer as data, the host row (`catalog/hosts.json`), this checkout's open work found by the ref the prompt names or this
session's mark, and the automation settings.

| # | Row | When | Answer |
|---|---|---|---|
| 1 | `envelope` | The host adapter marked the prompt synthetic (a task notification) | NONE |
| 2 | `opted-out` | An opt-out cue: "without orbit", "no orbit", "không dùng orbit" | NONE |
| 3 | `resume` | An open governed work of this checkout whose ref the prompt names, or this session's open work and a continue cue ("continue", "resume", "tiếp tục") | RESUME: the work, and its `resume` command |
| 4 | `conversational` | Intent `general`, or nothing selected beyond implicit providers and builtins | NONE |
| 5 | `mission` | `mission.orchestration` selected: Satellite's own signals, so the person asked for a mission | SATELLITE |
| 6 | `specification` | A workflow fits, and the prompt carries an acceptance-criteria cue or at least 3 list items | COORDINATED, `how: goal` |
| 7 | `several-owners` | A workflow fits, and the matched intents span a change (`development`, `autonomous-engineering`) and either a work item (`requirements`, a ref) or a verification owner (`investigation`, `security`) | COORDINATED, `how: automation` |
| 8 | `one-agent` | The top selection is a directly dispatchable agent | DIRECT: Agent `orbit:<agent>` |
| 9 | `one-skill` | Anything is selected | DIRECT: Skill `orbit:<skill>`; for a trivial edit the host's own tools are an accepted answer |
| 10 | `nothing` | Always | NONE |

Examples. The intents are 0.4.0's, plus the cue rows proposed here.

| Prompt | Matched | Strategy | Activation |
|---|---|---|---|
| "hi, how's it going?" / "chào bạn" | — | NONE | nothing |
| "explain what applyDiscount does" | `documentation` | NONE (nothing non-implicit selected) | nothing |
| "where would a payment-provider integration belong here?" | `architecture` | DIRECT | `orbit-architecture` |
| "rename qty to quantity in orders.mjs" | `development` | DIRECT | `orbit-develop`, or the host's own tools |
| "write a test plan for the refund screen" | `qa` (+ `qa.planning`) | DIRECT | `orbit-test-plan` |
| "why did the last UI test run fail?" | `qa` (+ `failure.classification`) | DIRECT | Agent `orbit-failure-analyst` |
| "implement the refund approval rule, verify authorization, update the tests and check for regression" | `development`, `qa`, `security` | COORDINATED, automation | `automation.mjs start` through `orbit-help` |
| a pasted PBI with five acceptance criteria | `requirements`, `development` | COORDINATED, goal | `orbit.mjs goal start --stdin` through `orbit` |
| "continue PBI-482" | `requirements` | RESUME | that work's workflow, resumed |
| "run this as a multi-agent mission" | — (Satellite signal) | SATELLITE | `satellite` |
| "without Orbit, rename qty to quantity" | `development` | NONE | nothing |

What the strategy does not do:

- **It does not make orbit-help a gateway.** DIRECT names the specialist. orbit-help keeps its own contract as the
  coordinator's entry and the navigator: a person who invokes `/orbit-help` with a task still gets a coordinated
  workflow, so B1 is unchanged.
- **It does not choose `orbit-engineer` for every change.** "Autonomously" and "until verified" select it; a plain
  change selects `orbit-develop`.
- **It never infers SATELLITE from words that sound complex.** A goal's structured reading may justify a mission later
  (M6), measured by B4 first.

### 5.6 Proactive subagent selection and dispatch

An agent is chosen by capability, like a skill. What decides between an agent and its skill:

| Situation | Choice | Why |
|---|---|---|
| A direct request, one owner | The skill, in the session | The person sees the work; no context is spawned for nothing |
| A diagnosis or repair that is one bounded job | The direct agent (`orbit-failure-analyst`, `orbit-dsl-doctor`) | Its own context keeps the parent's clean, and its profile is narrower than the session |
| A coordinated workflow step on a native-agent host | The step's agent (`src/automation/select.mjs:17`) | Unchanged |
| A `via` agent | Only from its parent skill's playbook | It needs the parent's preceding step: a classification, an envelope, a plan |
| Independent units to run at once | A Satellite mission, which dispatches up to its limit | The coordinator runs one step at a time by design (ADR 0022) |
| A protocol-2 host | Never an agent: the skill's own loop in the session | No native agents (`catalog/hosts.json`) |

**Unnecessary delegation is observed, not only benchmarked.** The activation fold
([§5.11](#511-the-activation-chain-and-independent-verification)) marks a turn `over-delegated` when it dispatched
agents the strategy did not account for: a `via` agent with no parent skill in the turn, or two dispatches of one agent
type for one work outside a mission.

### 5.7 Dynamic capability composition

The model decomposes; the engines validate. No new engine is added.

- **One specialist** is DIRECT.
- **Several owners, one objective** is COORDINATED through automation. Its existing graph (`DEPENDS`), replanning
  (`TRIGGERS`), per-step dispatch and owner-settled evidence do the rest. Capability words the request needs that no
  step kind implies are passed as `--capability`.
- **A specification** is COORDINATED through a goal. Its units are automation workflows, linked by `--goal`.
- **Separable units asked as a mission** are SATELLITE. Its gateway, profiles and independent verification do the rest.
- **Multiple sequential skills without a workflow** (for example "map the screen, then plan its tests") stay DIRECT,
  one skill after another, each named by the next prompt's routing or by the first skill's own NEXT. A plan that needs
  dependency tracking is COORDINATED.

One task keeps one work identity and evidence chain. `track` binds the request to one work, automation and goal starts
join it (`tracking` in their answer), and every owner record links back. That is ADR 0017 and the work-tracking
contract, unchanged.

### 5.8 Router v3 (B5 inside B22)

- **NONE adds nothing.** No header, no ADVICE line.
- **Low confidence** is shown only when a signal-gated provider's own signal hit.
- **The head outranks the tail.** Cues in the first 2,000 characters outrank cues from a pasted tail, a weight that is
  data in `terms.mjs`. A pasted log or file no longer decides the intent.
- **Vietnamese cues** are rows in `intents.mjs`: generic words, at most three terms, never a product.
- **A host envelope answers nothing.** The Claude adapter marks a prompt the host itself generated (a
  `<task-notification>`; M0 captures the fixture) as `synthetic`, and the router answers NONE for it.
- **Reachability rows**, as data, decided with the corpus: a `security` intent ("security", "access control",
  "authorization", "owasp", "asvs") requiring `security.assessment`; and refinements in `*` for reverse engineering,
  improvement, specifications and missions.
- **One added line, then the existing lines.** The text says the strategy and the activation path. For COORDINATED,
  RESUME and SATELLITE it gives the one command.
- **A routing corpus** of at least 100 English and 60 Vietnamese prompts, each with its expected intent, strategy and
  top selection (`test/fixtures/routing/corpus.jsonl`).
- **Unchanged:** fail-open, a 5-second timeout, no prompt text kept, ≤ 2 KB, and the existing router tests pass.

### 5.10 Continuous proactive behaviour: the lifecycle

Every answer below is a bounded addition by an existing subscriber, or one new subscriber. Every hook still exits 0 on
any error.

| Event | Today (0.4.0) | 0.5.0 | Only when | Bound |
|---|---|---|---|---|
| SessionStart | Lessons index, architecture and engineering memory lines; MCP and tool snapshots and the host-memory location in the background | One capability line: what Orbit can do here (families, usable counts, what a person switched off) and the project's STATUS word. On `resume` and `compact`, this session's open work and its next step. | Always one line; the open work only when one exists | ≤ 300 bytes for the new line |
| UserPromptSubmit | RouteDecision v2 text and the ADVICE line | Strategy and activation ([§5.5](#55-proactive-skill-selection-the-strategy-table), [§5.8](#58-router-v3-b5-inside-b22)) | Strategy ≠ NONE | ≤ 2 KB |
| PreToolUse (Skill, Agent) | Component switch refusal | Unchanged | | |
| PostToolUse (Agent `orbit:*`) | Trace only | One line for the parent: which owner record settles the agent's work and its current state. The agent's words are a report. | An `orbit:*` agent returned, and this session holds a governed workflow, goal, mission or task | One line |
| PostToolUseFailure | The failed run's diagnosis | Also, for an Orbit command that failed under this session's governed task: its owner's recovery row (`reconcile` reads it back; a write is never resent) | An Orbit CLI failed under a governed task | The same one payload: `dispatch` takes the first answer, so the line joins the existing one |
| SubagentStart, SubagentStop | Trace (`agent.started`, `agent.ended`) | Unchanged. A subagent's last message is never read (ADR 0044); the parent-side line above carries the follow-through. | | |
| Stop | Asynchronous observation and checkpoint | **A synchronous hold**: `decision: "block"` with the next ready step of this session's own workflow or goal | Every condition below holds | At most 2 per prompt |
| SessionEnd | Finalizer | Unchanged | | |

**The Stop hold**, the one place Orbit keeps the model going, holds only when all of these are true:

1. `trigger.holdOnStop` is on: an automation setting, default on, set only through Control's door, narrowed machine
   then project.
2. `stop_hook_active` is false. A held turn is never held again in a row.
3. The trail can count this prompt's holds (trace on), and there were fewer than 2. If the count cannot be read, the
   turn is not held.
4. This session's own workflow or goal (`src/live/association.mjs`) is running, has ready steps, has no question
   waiting for a person, and is not PAUSED, CANCELLED, WAITING_APPROVAL, BLOCKED or ended.
5. This turn ran a command of that workflow (trail `command.ran`: `automation` or `goal` with `start`, `step` or
   `settle`). A turn that only answered a question is never held.
6. The prompt carried no halt cue ("stop", "wait", "pause", "dừng").

Its reason names the ready steps and the one command (`automation.mjs context <task>`), or asks the model to say why it
stops. Each hold is written as `turn.held`.

What the lifecycle never does:

- create work from ordinary conversation;
- restart a settled task, or resend a write that did not settle;
- override a person's stop, pause or cancel;
- grant, approve or resume anything;
- add text on an ordinary tool call.

### 5.11 The activation chain and independent verification

A new pure fold, `src/trace/projections/activation.mjs`, reads the trail and a work-view reader handed in. It reuses
`suggestedEntries` and `invoked` from `turns.mjs`, and `trace.mjs activation` prints it, per turn and per work.

| Link | Means | Source | Basis (`src/attribution.mjs`) |
|---|---|---|---|
| Suggested | The router named it, with the strategy | `prompt.submitted` | Orbit's own decision |
| Model-selected | The model called Skill or Agent naming it | `skill.invoked`, `agent.invoked` (PreToolUse) | HOST_OBSERVED |
| Host-dispatched | The call passed the switch; the agent launched and started | `skill.invoked` outcome ok, `agent.launched`, `agent.started` | HOST_OBSERVED |
| Orbit-executed | An owner record was created or moved for this session | Task, workflow, goal, investigation and mission journals (`created.session`); the work's links | RUNTIME_BOUND |
| Owner-verified | The owner's own word | Task COMPLETED by its completion rows; an investigation's outcome; a frozen snapshot; an acceptance criterion verified; a mission VERIFIED; the work view `verified` | The owner's |

The turn's verdict extends `FOLLOW_VERDICTS` (`followed · diverged · not-invoked · nothing-suggested ·
nothing-routed`) with `over-delegated`. Only the owner-verified link may ever be called verified. The fold stores
nothing, so Control and the terminal cannot disagree about it.

### 5.12 Governance preserved

| Invariant | How this design keeps it |
|---|---|
| Autonomous by default within approved boundaries | No new boundary and no new approval. A hold never approves. |
| Primary checkout protection; push and production approvals | Untouched. The benchmark proves a push still waits (ORBIT-ACT-011). |
| Task-owned isolated workspaces | COORDINATED and SATELLITE use the engines that own them. |
| Independent evidence ownership; no model-reported PASS | Only an owner's record is verified; the activation fold reads owners. |
| Local machine store | No new room. One trace event and one setting. |
| No raw prompt in routing hooks | Shape counts and table words only; `synthetic` is a flag. |
| No privilege escalation through subagents | `via` agents only from parents; profiles stay `tools:` allowlists. M0 checks whether `Bash(<pattern>)` narrows the read-only agents. |
| No weakened acceptance test; no new dependency | Nothing loosened; zero dependencies. |
| No duplicate orchestrator or registry | One registry, three existing engines, one new pure table. |

## 6. Metadata review

### 6.1 Findings

- **Over budget, triggers last.** Every skill description is 368 to 1,017 characters (17,924 in total). The first
  sentence says what the skill is; "Use when" comes in the middle or at the end.
- **Overlapping triggers.**
  - `orbit`, `orbit-help` and `satellite` all promise "goal to verified outcome".
  - `orbit-develop` and `orbit-engineer` both implement a change.
  - `orbit-ui-test` and `orbit-test-suite` both provide `qa.execution`.
  - `orbit-qa` and `orbit-ui-explore` both explore.
  - `orbit-architecture`, `orbit-reverse-engineer` and `orbit-dotnet` all answer what a project is.
- **Generic signals.**
  - `orbit-test-suite`'s "run", "build" and "release" collide with runtime and release prompts.
  - `orbit-release`'s "orbit", "plugin" and "engine" match any prompt about Orbit, and "orbit" is listed twice.
  - `orbit-requirements`' bare "issue" is the word the intents table deliberately avoids
    (`src/routing/intents.mjs`, the comment on `requirements`).
- **Unclear delegation.**
  - Parent-only agents say so only deep in their descriptions.
  - `orbit-map-healer` and `orbit-qa-case-writer` can be selected directly.
  - Two skills name their agents by pattern.
  - One skill names an agent that does not exist.
- **Missing dependency.** `engineering.context` has no provider.

## 8. Release scope

**The minimum provable 0.5.0 for B22 is M0 + M1 + M2 + M4.** It shows, on the real Claude Code CLI in Docker and
against both a no-Orbit arm and the 0.4.0 plugin, that:

- Claude picks the right Orbit skill or agent unprompted;
- Claude stays silent on negatives;
- a switch is respected, and a push still waits for its approval;
- Claude composes through the coordinator when a request needs it.

**Recommended in 0.5.0 if the budget allows: M3**, because continuous behaviour is part of the ask. Its rows ship
recorded.

**B21 in 0.5.0** is M5's deterministic part: references verified against the tree, relevance from existing owners, and
sufficiency. Wider symbol retrieval follows it.

**Deferred to 0.6:** M6, file-level import graphs (language packs), and native proof on the other hosts.

**Operational cost, estimated.** M0 measures the real figures.

| Run | Cases | $ per arm-pass (assumed) | Arms | Total |
|---|---|---|---|---|
| Selection cases, three negatives included | 10 | 5–20 (0.5–2 each) | 3 | $15–60 |
| Outcome cases | 5 | 27–48 (a rename costs a dollar or two; a coordinated change runs up to its $15 limit) | 3 | $81–144 |
| **One recorded pass** | 15 | | | **≈ $100–200** |
| **A reliability pass** (3 repeats, B2) | | | | **≈ $300–600** |

Run one after another, a recorded pass is about 10 to 14 hours of cloud-session time: 45 runs, the selection runs taking minutes and the end-to-end runs up to an hour. The deterministic layer (corpus, catalog,
strategy, controls) costs nothing per run and gates the fast tier.

## 9. The answer today

**Not yet.**

- Claude Code can see Orbit's skills and agents and can invoke them.
- Orbit's descriptions overflow the host's listing and put their triggers last.
- The router's suggestions are noisy and decide no strategy, and three background notifications in this session were
  routed as `investigation`.
- Nothing proves selection, abstention or composition with the real CLI.

**The smallest concrete implementation that demonstrates it is M0 + M1 + M2 + M4:**

1. Trigger-first descriptions within budget, and `via` for parent-only agents.
2. The strategy table and router v3, which is silent for NONE.
3. The activation suite: 15 cases, with controls for idle, over-eager, forging, half and escalating hosts, run with
   the real Claude Code CLI against no-Orbit and 0.4.0 baselines.

That proves, or refutes with numbers, that a developer can use Claude Code normally and get the right Orbit capability
unprompted. The verified outcomes come from the owners Orbit already has. Open questions for the owner are in
[the backlog](0.5.0.md#open-questions-for-the-owner).
