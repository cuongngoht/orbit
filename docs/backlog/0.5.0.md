# Orbit 0.5.0 backlog

**Status:** proposed — the owner confirms the open questions at the end before work starts.
**Drafted:** 2026-11-03, while 0.4.0 was being qualified.
**Source:** what the 0.4.0 autonomous ships (ADR 0049) showed, and the gaps the owner named while they ran.

## Theme

0.4.0 proves each autonomous capability **on its own**, carried by the real Claude Code in Docker:

- engineering goals (the E2E cases);
- QA investigations (the QA cases);
- self-repair (ORBIT-SRC-001).

0.5.0 proves the paths people actually use, and measures how often they work:

- **code and QA together**, entered through `/orbit-help`;
- **how reliable** each model-carried row is, including on cases nobody tuned Orbit against;
- **whether memory makes a second session better**, and never worse;
- **Satellite missions** with a real host.

## Ground rules (carried over from 0.4.0)

- **Never loosen to pass.** Never loosen an acceptance rule, a case's ground truth, the verifier or `ship/policy.json`
  to get a PASS. A failing row is diagnosed from its run room first (CLAUDE.md, "Shipping a release from Claude Code
  cloud").
- **New rows are recorded first.** A new benchmark row starts **recorded, not required**, like native host acceptance.
  It becomes required only through the promotion rule in [Release criteria](#release-criteria-for-050).
- **Every engine change is proven.** It ships with a regression test that fails before the change, plus the full suite
  and the strict Five Lines lint.
- **Every new case proves its checks.** It ships with controls that show its checks discriminate: a host that does
  nothing, a host that cheats, and a host that does only half.
- **Versioning.** Contract changes follow AGENTS.md "Definition of done": an addition is minor, and 0.5.0 is a minor
  release.

## B1 — Code + QA in one workflow, through `/orbit-help`

**Problem.**
- A change request to `/orbit-help` starts the `engineering` workflow (`src/automation/workflows.mjs`): requirement →
  context → runtime → engineering → **qa** → regression → review.
- The QA step runs only when the runtime step can start the app.
- 0.4.0 benchmarked engineering (E2E) and QA (QA) separately.
- Nothing runs the whole chain with a real host, and nothing checks that the QA step actually ran on the change.

**Scope.**
- A new case kind `workflow` (proposed ADR) and a suite `orbit-workflow`.
  - The host gets a natural-language request through `/orbit-help`.
  - It runs against the acceptance invoice app, which starts in the task's sandbox.
  - The request needs a code change, and a defect is planted next to it: in the code the change touches or calls.
- Graded on three independent things, all from records and never from the host's word:
  1. **The code:** hidden checks, as in E2E.
  2. **The QA:** the planted defect is found on the changed app, with no false alarm on the clean app, as in QA
     (ADR 0047).
  3. **The path:** the workflow's own journal shows each step settled on its owner's record. That means:
     - routing chose `engineering`;
     - the QA step ran on the change's sandbox and was not skipped;
     - regression and review both settled.
- Three or four cases:
  - a change and a defect in the same component;
  - a change and a defect in an async path;
  - a request that should route to `investigation` (no code change);
  - a request with nothing startable. QA must be reported as skipped, with its reason, never silently.

**Controls.**
- An idle host.
- A code-only host that skips QA: it must FAIL on (2).
- A host that edits the developer's checkout or bypasses the workflow: it must FAIL on (3).
- A scripted reference host that passes.

**Done when:**
- every control holds in CI's conformance tier;
- each case passes with Opus on at least 3 of 5 runs, recorded in `metrics`;
- a skipped QA step is visible in the `/orbit-help` output and in Live.

## B2 — Reliability and generalisation

**Problem.**
- A release needs each model-carried row to PASS once; with `--retries`, that is up to three runs.
- That says nothing about how often the row works.
- Every 0.4.0 fix was found on these same cases, so there is a risk of tuning Orbit to them.

**Scope.**
- **Repeat runs.** `benchmark/run.mjs run --repeat=N` (with `--suite` too).
- **Rates in `metrics`.** `metrics` reports pass@1, pass@k, median cost and median minutes per row and per model, by
  revision (`--by=revision` already exists).
- **A held-out fixture.** A second application in a different domain, for example an order/inventory service with its
  own async worker and tenancy, with its own QA and E2E cases.
  - Its author did not read the 0.4.0 failure reports.
  - Nobody tunes Orbit against it before its first run.
- **A reliability report.** `ship.mjs` writes it next to `evidence.json`: the rates over the last N runs on the release
  revision. The release notes quote it.

**Done when:**
- one release candidate has at least 5 Opus runs and at least 3 Sonnet runs per model-carried row;
- the held-out suite runs;
- the report is published with the release.

**Targets (proposed; the owner confirms):**
- E2E pass@1 ≥ 90% on Opus.
- QA pass@1 ≥ 70% on Opus.
- The held-out suites within 15 points of the tuned ones.

## B3 — Memory effectiveness

**Problem.**
- `orbit-memory` (MEM-001..006) proves memory keeps its rules: sessions, authority, staleness, crash safety.
- Nothing measures whether memory helps a host the next time.
- Nothing measures how much a wrong memory hurts.

**Scope.**
1. **Deterministic, no model.**
   - A second `architecture ensure` or knowledge recall on an unchanged checkout is CURRENT and reads no file.
   - After a scoped change, only that scope is read again.
   - Measure git calls, files read and wall time.
   - These are source cases in `orbit-memory`.
2. **A/B with a real host.**
   - A multi-session case kind (proposed ADR) keeps the run's store between sessions.
   - Session 1 learns.
   - Session 2 runs once with memory and once with `ORBIT_LEARN=off` and `ORBIT_HOST_MEMORY=off`.
   - At least 3 repeats per arm, on 2–3 QA cases, ORBIT-QA-003 among them.
   - Compare pass rate, decisions used, designs refused, cost and minutes.
3. **A poisoned-memory control.**
   - Plant a wrong lesson or a stale fact.
   - The host must not skip a check or raise a false alarm because of it. Memory is a hint, never a truth (AGENTS.md).

**Done when:**
- (1) is required;
- (2) and (3) are recorded with their effect sizes;
- a short write-up says what memory buys and what it costs.

## B4 — Satellite with a real host

**Problem.**
- `orbit-satellite` (SAT-001..004) checks Satellite's source: its decisions and how evidence settles.
- No mission has run with a real host.

**Scope.**
- A case kind `mission`: Satellite gets a goal, either a bug with its verification or a small feature.
- Graded by hidden checks, plus two record checks:
  - every acceptance criterion settled on an independent owner's record, never on an agent's report;
  - each work unit's agent stayed inside its least-privilege profile.
- Two cases.

**Controls.**
- A mission that claims success with no owner record: it must FAIL.
- An idle host.

**Done when:** the controls hold and an Opus PASS is recorded.

## B5 — Router accuracy, Vietnamese included

**Problem.**
- During the 0.4.0 release session, the `UserPromptSubmit` router hook attached a low-confidence suggestion to most of
  the owner's Vietnamese messages. For example:
  - `orbit-report`, a product-owner project report, for "tới đâu rồi" ("how far along is it");
  - `orbit-test-suite` and a playwright that is not installed, for a question about benchmark history.
- It also added the same "Orbit coordinates a task by default" line to every prompt.
- Low-confidence intents are shown anyway. `confidenceOf` (`src/routing/classify.mjs:44`) calls one cue "low".

**Scope.**
- **A routing corpus test** in English and Vietnamese, at least 100 prompts: status questions, chit-chat, code changes,
  QA and reports. Each prompt names its expected intent, or `none`.
- **A `none` (conversational) outcome** that suppresses the hint.
- **Low-confidence suggestions** shown only when a skill is plausibly wanted.
- **Vietnamese terms** in the routing vocabulary, as data and never code (AGENTS.md, "The vocabulary is data").

**Done when:**
- corpus accuracy is at least 90%;
- conversational prompts get no suggestion;
- the hook's output for high-confidence English prompts is unchanged (the existing `router*.test.mjs`).

## B6 — Ship ergonomics

What the 0.4.0 release (twelve ships) asked for:

- **`ship.mjs --precheck`.**
  - Runs only the model-carried rows, each once, with no fail-fast, before the ~90 minutes of controls.
  - Prints every failure with its run room.
  - 0.4.0 did this by hand; see CLAUDE.md.
- **Survive a cloud worker restart without losing a long row.**
  - A row's benchmark run can be resumed from its own room.
  - The source-case control rows take ~20 minutes each.
- **A failed model-carried row prints its diagnosis bundle in `--status`:**
  - relay refusals;
  - `result.stopped`;
  - the host's finish reason;
  - the budget it used.
  Diagnosing then needs no manual reading of the room.
- **Flag names in limit errors.** An out-of-bounds `--retries` is refused as `--autonomousRetries is 0..3`. Name the
  flag a person typed.

- **Resume dead ends found while fixing ship 14** (each confirmed by a probe test):
  - a failed image build is never rebuilt after a resume (NEXT's NOT_BUILT checks only that a build record exists), so
    rows can run on images already present -- an evidence gap, likely with Docker Hub 429s;
  - a ship blocked at the host check re-blocks on resume without asking the host again;
  - on resume RECONCILE runs before PREFLIGHT, so a read-back row skips the content-digest part of WRONG_TREE;
  - the stage stays ENVIRONMENT after a resume while rows run;
  - an interrupted run counts its whole allowance as cost, so repeated interruptions spend `--usd`;
  - an interrupted `release.repair` round is still UNTRUSTED and spends a repair attempt.

**Done when:** each feature has a test, and the next release's ship uses them.

## B7 — Engine carry-overs, found while diagnosing 0.4.0

Each one is confirmed, then either fixed with a regression test or closed with a reason.

- **A fault control with no witness can be SATISFIED when the fault never fired.** That PASS is not earned (AGENTS.md,
  "PASS is earned"). Decide between:
  - requiring a witness step for every fault control; or
  - ruling INCONCLUSIVE when no observation carried the point.
- **`observerRef` on scheduler and worker operations.**
  - `orbit.scheduler.observe` and the worker operations accept an `observerRef`.
  - The binder binds an observer only to a channel (`src/runtime/sandbox/bindings.mjs`).
  - Generation accepts the ref, then sandbox preparation blocks it.
  - Fix: refuse it at generation, or drop it from the family table.
- **An interrupted worker's envelope reads as "another case".**
  - An interrupted worker writes an envelope with no `caseDigest` (`cli/sandbox-worker.mjs`).
  - It is judged EXECUTION_ERROR, with the misleading "ran another case" finding (`src/run/envelope.mjs`).
  - Fix: give it its own outcome, without making a run that may have written free to retry.
- **Adapter request shapes.**
  - `orbit.adapter/v1` operations declare no shape for `request` (`src/adapters/contract-v1.mjs`).
  - So a wrong `request.businessKey` is refused only at run time.
  - Fix: an optional `request` table per operation, checked at generation.
  - Needs an `extend.md` row and an ADR, and re-records the conformance receipts, because adapter fingerprints change.
- **Per-obligation budgets.** The design and repair budgets per obligation (4 designs, 2 repairs by default) are not in
  `context.budget`. Show them.
- **Stale module map.** `docs/agents/layout.md`, in the sandbox section around line 556, names `fixture-policy.mjs`,
  `test-faults.mjs` and `replay-policy.mjs`. None of them exist.
- **QA on Sonnet.**
  - The orbit-qa playbook gets one generic worked design per obligation shape, never the acceptance designs, so that a
    host's first design compiles.
  - B2 records Sonnet's QA pass@1.

## B9 — Tool-call failures: measured per tool, and cases that make tools fail

The owner's team dashboard shows Claude Code's tool use per tool, with calls and failures (one week: Bash 717 calls,
28 failed; every other tool 0 failed). Orbit's benchmark keeps the host's whole stream (`rounds/1/out/host.jsonl`) and
every relay request with its exit code, but nothing counts how often a host's tool call failed, which tool, or why. In
the 0.4.0 QA rows every run spent at least one call on a refused `--help` probe to the relay.

**Measure (in the B2 report, per suite and per model):**
- per tool: calls, failed calls, failure rate -- from the host's own stream (a tool result marked as an error);
- per relay subcommand: requests, refusals by reason, nonzero exits (`relay.jsonl`);
- failed calls per PASS, and turns and cost spent after a failed call before the next useful one.

**Cases that make tools fail on purpose** (a new group in the engineering and QA suites; each has a scripted control
and a model-carried row):
- a declared check that fails first and passes once the defect is fixed;
- a relay request refused with its reason (a wrong flag, a ref that does not exist), where the host must read the
  reason and correct the call, never repeat it;
- a command that times out or is interrupted, where the host must read the run back, never resend a write;
- a tool the host expects that is missing, where the host reports the gap, never invents a workaround outside Orbit.
The verifier holds each to: the host recovered, the same failing call was not repeated more than a bound, and nothing
was written outside the task's own workspace.

**Reduce what Orbit causes:**
- every refusal names the one thing to do instead (the `--help` probe gets the subcommand's usage, not a bare refusal);
- the playbooks show the exact relay calls, so a host never guesses a flag.

**Done when:** the B2 report shows tool-call failure rates per tool and relay subcommand; the new cases' controls hold;
and their model-carried rows are recorded, with the repeated-failing-call bound held.

## Release criteria for 0.5.0

- Everything 0.4.0 required, on the release commit (ADR 0049).
- The new suites (B1, B3, B4) are present, with every control held. Their model-carried rows are recorded.
- **Promotion rule (proposed):** a recorded model-carried row becomes required in the release after the one in which it
  reached pass@1 ≥ 80% over at least 5 Opus runs.
- The reliability report (B2) is published with the release notes, with B9's tool-call failure rates in it.
- CLAUDE.md "Shipping a release from Claude Code cloud" is updated with what the 0.5.0 ships taught.
