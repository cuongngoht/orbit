# Orbit 0.5.0 backlog

**Status:** proposed — the owner confirms the open questions at the end before work starts.
**Drafted:** 2026-11-03, while 0.4.0 was being qualified.
**Revised:** 2026-11-05: B21, B22 and B23 added, for proactive skill and agent orchestration. Their design is in
[0.5.0-proactive-orchestration.md](0.5.0-proactive-orchestration.md), the decision in
[ADR 0050](../adr/0050-the-host-activates-orbit-by-capability-and-orbit-verifies-what-happened.md) (proposed), and the
proof in [0.5.0-activation-benchmark.md](0.5.0-activation-benchmark.md).
**Source:** what the 0.4.0 autonomous ships (ADR 0049) showed, and the gaps the owner named while they ran.

## Theme

0.4.0 proves each autonomous capability **on its own**, carried by the real Claude Code in Docker:

- engineering goals (the E2E cases);
- QA investigations (the QA cases);
- self-repair (ORBIT-SRC-001).

0.5.0 proves the paths people actually use, and measures how often they work:

- **code and QA together**, entered through `/orbit-help`;
- **how reliable** each model-carried row is, including on cases nobody tuned Orbit against;
- **whether memory makes a second session better**, and never worse;
- **Satellite missions** with a real host;
- **whether Claude Code uses Orbit by itself**: the right skill or agent unprompted, several composed when a request
  needs them, and nothing when nothing helps.

## Ground rules (carried over from 0.4.0)

- **Never loosen to pass.** Never loosen an acceptance rule, a case's ground truth, the verifier or `ship/policy.json`
  to get a PASS. A failing row is diagnosed from its run room first (CLAUDE.md, "Shipping a release from Claude Code
  cloud").
- **New rows are recorded first.** A new benchmark row starts **recorded, not required**, like native host acceptance.
  It becomes required only through the promotion rule in [Release criteria](#release-criteria-for-050).
- **Every engine change is proven.** It ships with a regression test that fails before the change, plus the full suite
  and the strict Five Lines lint.
- **Every new case proves its checks.** It ships with controls that show its checks discriminate: a host that does
  nothing, a host that cheats, and a host that does only half.
- **Versioning.** Contract changes follow AGENTS.md "Definition of done": an addition is minor, and 0.5.0 is a minor
  release.

## B1 — Code + QA in one workflow, through `/orbit-help`

**Problem.**
- A change request to `/orbit-help` starts the `engineering` workflow (`src/automation/workflows.mjs`): requirement →
  context → runtime → engineering → **qa** → regression → review.
- The QA step runs only when the runtime step can start the app.
- 0.4.0 benchmarked engineering (E2E) and QA (QA) separately.
- Nothing runs the whole chain with a real host, and nothing checks that the QA step actually ran on the change.

**Scope.**
- A new case kind `workflow` (proposed ADR) and a suite `orbit-workflow`.
  - The host gets a natural-language request through `/orbit-help`.
  - It runs against the acceptance invoice app, which starts in the task's sandbox.
  - The request needs a code change, and a defect is planted next to it: in the code the change touches or calls.
- Graded on three independent things, all from records and never from the host's word:
  1. **The code:** hidden checks, as in E2E.
  2. **The QA:** the planted defect is found on the changed app, with no false alarm on the clean app, as in QA
     (ADR 0047).
  3. **The path:** the workflow's own journal shows each step settled on its owner's record. That means:
     - routing chose `engineering`;
     - the QA step ran on the change's sandbox and was not skipped;
     - regression and review both settled.
- Three or four cases:
  - a change and a defect in the same component;
  - a change and a defect in an async path;
  - a request that should route to `investigation` (no code change);
  - a request with nothing startable. QA must be reported as skipped, with its reason, never silently.

**Controls.**
- An idle host.
- A code-only host that skips QA: it must FAIL on (2).
- A host that edits the developer's checkout or bypasses the workflow: it must FAIL on (3).
- A scripted reference host that passes.

**Done when:**
- every control holds in CI's conformance tier;
- each case passes with Opus on at least 3 of 5 runs, recorded in `metrics`;
- a skipped QA step is visible in the `/orbit-help` output and in Live.

## B2 — Reliability and generalisation

**Problem.**
- A release needs each model-carried row to PASS once; with `--retries`, that is up to three runs.
- That says nothing about how often the row works.
- Every 0.4.0 fix was found on these same cases, so there is a risk of tuning Orbit to them.

**Scope.**
- **Repeat runs.** `benchmark/run.mjs run --repeat=N` (with `--suite` too).
- **Rates in `metrics`.** `metrics` reports pass@1, pass@k, median cost and median minutes per row and per model, by
  revision (`--by=revision` already exists).
- **A held-out fixture.** A second application in a different domain, for example an order/inventory service with its
  own async worker and tenancy, with its own QA and E2E cases.
  - Its author did not read the 0.4.0 failure reports.
  - Nobody tunes Orbit against it before its first run.
- **A reliability report.** `ship.mjs` writes it next to `evidence.json`: the rates over the last N runs on the release
  revision. The release notes quote it.

**Done when:**
- one release candidate has at least 5 Opus runs and at least 3 Sonnet runs per model-carried row;
- the held-out suite runs;
- the report is published with the release.

**Targets (proposed; the owner confirms):**
- E2E pass@1 ≥ 90% on Opus.
- QA pass@1 ≥ 70% on Opus.
- The held-out suites within 15 points of the tuned ones.

## B3 — Memory effectiveness

**Problem.**
- `orbit-memory` (MEM-001..006) proves memory keeps its rules: sessions, authority, staleness, crash safety.
- Nothing measures whether memory helps a host the next time.
- Nothing measures how much a wrong memory hurts.

**Scope.**
1. **Deterministic, no model.**
   - A second `architecture ensure` or knowledge recall on an unchanged checkout is CURRENT and reads no file.
   - After a scoped change, only that scope is read again.
   - Measure git calls, files read and wall time.
   - These are source cases in `orbit-memory`.
2. **A/B with a real host.**
   - A multi-session case kind (proposed ADR) keeps the run's store between sessions.
   - Session 1 learns.
   - Session 2 runs once with memory and once with `ORBIT_LEARN=off` and `ORBIT_HOST_MEMORY=off`.
   - At least 3 repeats per arm, on 2–3 QA cases, ORBIT-QA-003 among them.
   - Compare pass rate, decisions used, designs refused, cost and minutes.
3. **A poisoned-memory control.**
   - Plant a wrong lesson or a stale fact.
   - The host must not skip a check or raise a false alarm because of it. Memory is a hint, never a truth (AGENTS.md).

**Done when:**
- (1) is required;
- (2) and (3) are recorded with their effect sizes;
- a short write-up says what memory buys and what it costs.

## B5 — Router accuracy, Vietnamese included

**Problem.**
- During the 0.4.0 release session, the `UserPromptSubmit` router hook attached a low-confidence suggestion to most of
  the owner's Vietnamese messages. For example:
  - `orbit-report`, a product-owner project report, for "tới đâu rồi" ("how far along is it");
  - `orbit-test-suite` and a playwright that is not installed, for a question about benchmark history.
- It also added the same "Orbit coordinates a task by default" line to every prompt.
- Low-confidence intents are shown anyway. `confidenceOf` (`src/routing/classify.mjs:44`) calls one cue "low".

**Scope.**
- **A routing corpus test** in English and Vietnamese, at least 100 prompts: status questions, chit-chat, code changes,
  QA and reports. Each prompt names its expected intent, or `none`.
- **A `none` (conversational) outcome** that suppresses the hint.
- **Low-confidence suggestions** shown only when a skill is plausibly wanted.
- **Vietnamese terms** in the routing vocabulary, as data and never code (AGENTS.md, "The vocabulary is data").

**Done when:**
- corpus accuracy is at least 90%;
- conversational prompts get no suggestion;
- the hook's output for high-confidence English prompts is unchanged (the existing `router*.test.mjs`).

**Folded into B22.** B5 lands inside B22's router work (M2). The corpus also names each prompt's expected strategy, and
B5's own done-when is unchanged.

## B6 — Ship ergonomics

What the 0.4.0 release (twelve ships) asked for:

- **`ship.mjs --precheck`.**
  - Runs only the model-carried rows, each once, with no fail-fast, before the ~90 minutes of controls.
  - Prints every failure with its run room.
  - 0.4.0 did this by hand; see CLAUDE.md.
- **Survive a cloud worker restart without losing a long row.**
  - A row's benchmark run can be resumed from its own room.
  - The source-case control rows take ~20 minutes each.
- **A failed model-carried row prints its diagnosis bundle in `--status`:**
  - relay refusals;
  - `result.stopped`;
  - the host's finish reason;
  - the budget it used.
  Diagnosing then needs no manual reading of the room.
- **Flag names in limit errors.** An out-of-bounds `--retries` is refused as `--autonomousRetries is 0..3`. Name the
  flag a person typed.

- **Resume dead ends found while fixing ship 14** (each confirmed by a probe test):
  - a failed image build is never rebuilt after a resume (NEXT's NOT_BUILT checks only that a build record exists), so
    rows can run on images already present -- an evidence gap, likely with Docker Hub 429s;
  - a ship blocked at the host check re-blocks on resume without asking the host again;
  - on resume RECONCILE runs before PREFLIGHT, so a read-back row skips the content-digest part of WRONG_TREE;
  - the stage stays ENVIRONMENT after a resume while rows run;
  - an interrupted run counts its whole allowance as cost, so repeated interruptions spend `--usd`;
  - an interrupted `release.repair` round is still UNTRUSTED and spends a repair attempt.

**Done when:** each feature has a test, and the next release's ship uses them.

## B7 — Engine carry-overs, found while diagnosing 0.4.0

Each one is confirmed, then either fixed with a regression test or closed with a reason.

- **A fault control with no witness can be SATISFIED when the fault never fired.** That PASS is not earned (AGENTS.md,
  "PASS is earned"). Decide between:
  - requiring a witness step for every fault control; or
  - ruling INCONCLUSIVE when no observation carried the point.
- **`observerRef` on scheduler and worker operations.**
  - `orbit.scheduler.observe` and the worker operations accept an `observerRef`.
  - The binder binds an observer only to a channel (`src/runtime/sandbox/bindings.mjs`).
  - Generation accepts the ref, then sandbox preparation blocks it.
  - Fix: refuse it at generation, or drop it from the family table.
- **An interrupted worker's envelope reads as "another case".**
  - An interrupted worker writes an envelope with no `caseDigest` (`cli/sandbox-worker.mjs`).
  - It is judged EXECUTION_ERROR, with the misleading "ran another case" finding (`src/run/envelope.mjs`).
  - Fix: give it its own outcome, without making a run that may have written free to retry.
- **Adapter request shapes.**
  - `orbit.adapter/v1` operations declare no shape for `request` (`src/adapters/contract-v1.mjs`).
  - So a wrong `request.businessKey` is refused only at run time.
  - Fix: an optional `request` table per operation, checked at generation.
  - Needs an `extend.md` row and an ADR, and re-records the conformance receipts, because adapter fingerprints change.
- **Per-obligation budgets.** The design and repair budgets per obligation (4 designs, 2 repairs by default) are not in
  `context.budget`. Show them.
- **A Windows test flakes under load.** "three real hook processes share a trace store, dedupe new delivery and retain no
  raw payload" failed once on `check (windows-latest, 20)` for 8a1166c and passed on re-run. Make it deterministic (its
  three processes race on one trace store), never retry it into green.
- **What 0.4.0's last fixes left open** (each found by a real host): a host may now meet a refusal where it met a false
  alarm -- an effect-once design that observes only the duplicate has no accepted slot to rule it, so consider a "settled"
  barrier template; and a key a criterion states `for` another shape could be flagged at the first design, not only the
  second (`src/qa/backend/shared.mjs`).
- **Stale module map.** `docs/agents/layout.md`, in the sandbox section around line 556, names `fixture-policy.mjs`,
  `test-faults.mjs` and `replay-policy.mjs`. None of them exist.
- **QA on Sonnet.**
  - The orbit-qa playbook gets one generic worked design per obligation shape, never the acceptance designs, so that a
    host's first design compiles.
  - B2 records Sonnet's QA pass@1.

## B9 — Tool-call failures: measured per tool, and cases that make tools fail

The owner's team dashboard shows Claude Code's tool use per tool, with calls and failures (one week: Bash 717 calls,
28 failed; every other tool 0 failed). Orbit's benchmark keeps the host's whole stream (`rounds/1/out/host.jsonl`) and
every relay request with its exit code, but nothing counts how often a host's tool call failed, which tool, or why. In
the 0.4.0 QA rows every run spent at least one call on a refused `--help` probe to the relay.

**Measure (in the B2 report, per suite and per model):**
- per tool: calls, failed calls, failure rate -- from the host's own stream (a tool result marked as an error);
- per relay subcommand: requests, refusals by reason, nonzero exits (`relay.jsonl`);
- failed calls per PASS, and turns and cost spent after a failed call before the next useful one.

**Where the failures come from: the sandbox.** The owner's reading (2026-11-04): most failed tool calls come from the
tests that build a sandbox -- above all `orbit-engineer` (a task's own workspace, its dependency restore, its container
definition, its isolated topology) and the `/orbit` goal, which starts engineering tasks in turn. A host that drives
those through Bash meets Docker, ports, image pulls, restores and readiness waits, and each can fail. So the metric is
also kept per sandbox step:
- per sandbox step (`sandbox-prepare`, restore, container build, `sandbox-start`, readiness, `sandbox-stop`/release):
  attempts, failures, and the class of each (Docker absent or down, image pull refused or rate-limited, port held,
  restore failed, readiness never answered, a teardown that could not be proven);
- how many host tool calls each sandbox failure cost before the host got past it, or stopped;
- whether a failure the environment caused ended BLOCKED with its reason, and never as a FAIL of the change or a
  loop of Bash retries.

**Cases that make tools fail on purpose** (a new group in the engineering and QA suites; each has a scripted control
and a model-carried row):
- a declared check that fails first and passes once the defect is fixed;
- a relay request refused with its reason (a wrong flag, a ref that does not exist), where the host must read the
  reason and correct the call, never repeat it;
- a command that times out or is interrupted, where the host must read the run back, never resend a write;
- a tool the host expects that is missing, where the host reports the gap, never invents a workaround outside Orbit.
- sandbox failures in `orbit-engineer` and in an `/orbit` goal: Docker down, an image pull refused, a port already
  held, a restore that fails, a container that never becomes ready, where the task must end BLOCKED naming the cause
  and the one thing a person does, the host must not work around it by hand (no `docker run` of its own, no freeing a
  port), and nothing Orbit did not start may be stopped.
The verifier holds each to: the host recovered, the same failing call was not repeated more than a bound, and nothing
was written outside the task's own workspace.

**Reduce what Orbit causes:**
- every refusal names the one thing to do instead (the `--help` probe gets the subcommand's usage, not a bare refusal);
- the playbooks show the exact relay calls, so a host never guesses a flag.

**Done when:** the B2 report shows tool-call failure rates per tool and relay subcommand; the new cases' controls hold;
and their model-carried rows are recorded, with the repeated-failing-call bound held.

## B21 — Intent understanding and contextual discovery

**Priority:** P0. Design: [0.5.0-proactive-orchestration.md](0.5.0-proactive-orchestration.md) §5.3 and §5.4.

**Problem.**
- A host chooses what to do before anything says which code a request touches.
  - `cli/context.mjs --for` has no relevant-code section.
  - It matches by tokens only.
  - It carries freshness as text inside each section.
- Only the `/orbit` goal path reads a request into typed rows. Elsewhere, intent is a keyword table's.
- Nothing says whether there is enough evidence to proceed, so a host either guesses or asks too much.

**Scope.**
- **No new intent contract.** The goal analysis is the structured reading. It already separates explicit, derived,
  assumption, unknown, conflict and decision rows, each citing the persisted spec. `constraint` joins its kinds.
- **Which owner reads a request:**
  - a specification goes to the goal domain;
  - one objective that needs several owners goes to automation, with the host's declared `--intent`, never classified
    again from keywords;
  - a work item goes to the requirements domain.
- **A `relevant` section in the context package.**
  - Candidates come from the owners that hold evidence: architecture facts, the system graph, intelligence
    integrations, knowledge claims, engineering recall, the working set, `impact.mjs` reach and `obligations.mjs`
    checks.
  - References the host proposes are verified against the tracked tree.
  - Each item carries a class (`direct · dependency · downstream · verification · unknown`), its evidence, its
    freshness and who found it. At most 40 items.
- **A `sufficiency` word:** `ENOUGH`, `DISCOVER` or `ASK`, by an ordered table. `ASK` goes only through the existing
  question flow.
- **The playbooks use it.** `orbit-develop`, `orbit-engineer` and `orbit-help` read `sufficiency` before choosing
  scope.
- **No embeddings and no dependency.** File-level import graphs stay in language packs.

**Dependencies.** B22's router (M2) passes a declared intent along. The architecture, intelligence and knowledge owners
are unchanged. B2's harness runs the grounding cases.

**Acceptance criteria.**
- A reference the tracked tree does not hold is refused by name, and never listed.
- Every listed item names its evidence and freshness, and a package never holds more than 40.
- `ASK` is reached only when no source can settle a blocking unknown.
- A specification's planted ambiguity is never read as `explicit` (ORBIT-CTX-002 and 003, recorded).

**Done when:**
- the deterministic tests are required in the fast tier;
- ORBIT-CTX-001 to 003 are recorded, with recall, invented references and bytes read;
- README and the three playbooks say what the code does.

## B22 — Universal proactive skill and agent orchestration

**Priority:** P0. Design: [0.5.0-proactive-orchestration.md](0.5.0-proactive-orchestration.md). Decision:
[ADR 0050](../adr/0050-the-host-activates-orbit-by-capability-and-orbit-verifies-what-happened.md). Proof:
[0.5.0-activation-benchmark.md](0.5.0-activation-benchmark.md).

**Problem.**
- Claude Code picks a skill from its description.
  - Orbit's 25 skill descriptions total 17,924 characters, with their triggers last.
  - The listing drops descriptions when it overflows. The session that drafted this item showed `orbit:satellite`
    without one.
- The router misroutes.
  - Its suggestions are noisy.
  - It routes the host's own notifications as prompts.
  - It decides no strategy.
- Components are wired wrongly.
  - Five skills are unreachable by the router.
  - Two parent-only agents can be suggested straight from a prompt.
  - One skill names an agent that does not exist.
- Nothing follows through after an action.
  - Nothing holds a governed workflow to its next step when a turn ends.
  - Nothing tells the parent which record settles a returned agent's work.
- Nothing proves selection, abstention or composition with the real CLI. Every 0.4.0 benchmark prompt names its skill.

**Scope.** The milestones of the design, each shipped on its own:
- **M0, measure and confirm.** No product code: listing cost, native fixtures, a baseline run of the activation prompts
  on 0.4.0.
- **M1, metadata.**
  - Trigger-first descriptions: at most 300 characters each, and the 25 skills at most 7,500 together.
  - `via` on agent rows that only a parent skill dispatches.
  - The stale and pattern-only agent names fixed.
  - An `engineering-memory` builtin for `engineering.context`.
- **M2, the router and the strategy (B5 inside).**
  - One table answers NONE, DIRECT, COORDINATED, SATELLITE or RESUME.
  - Nothing is added for NONE.
  - Vietnamese cues, and host envelopes ignored.
  - Rows that reach the five unreachable skills.
  - A corpus of at least 100 English and 60 Vietnamese prompts.
  - orbit-help keeps its contract.
- **M3, the lifecycle and the activation fold.**
  - A session-start digest.
  - One line after an `orbit:*` agent returns, and the owner's recovery row after a failed Orbit command.
  - A bounded Stop hold (`trigger.holdOnStop`, `turn.held`).
  - `trace.mjs activation`: suggested → selected → dispatched → executed → verified.
- **M4, the activation benchmark.** A case kind `activation`, 15 cases, controls for idle, over-eager, forging, half
  and escalating hosts, and three arms (B23).

**Dependencies.**
- B5, which lands inside M2.
- B8: model-carried runs in cloud sessions only.
- B2's harness: `--repeat`, and the mechanism for recorded rows.
- B9's tool-failure metric.
- M0 comes before M1 to M3.

**Acceptance criteria.**
- **Metadata.** Every skill description is at most 300 characters and the total at most 7,500. Every agent's first
  sentence says whether it is direct or dispatched by its parent. A test holds both.
- **Wiring.** Every `via` names a skill whose SKILL.md names the agent, and no skill names an agent that does not
  exist. Every proactively usable component is reachable from an intent, a refinement or a need.
- **Router and strategy.**
  - The routing corpus scores at least 90 % on intent and on strategy.
  - Conversational prompts and host envelopes get no text.
  - The existing router tests pass unchanged.
  - The strategy table's last row always matches, SATELLITE is never inferred, and orbit-help's tests pass unchanged.
- **The Stop hold** never holds when:
  - `stop_hook_active` is set;
  - the prompt has already been held twice;
  - the workflow is paused, cancelled, waiting or blocked;
  - the turn ran no command of the workflow;
  - the prompt carried a halt cue;
  - tracing or the setting is off.
- **The activation suite.** Every control holds, and one Opus run per case per arm is recorded.

**Done when:**
- M0, M1, M2 and M4 have landed with their tests (M3 recommended);
- the activation suite's controls hold in CI's conformance tier;
- its model-carried rows are recorded in a Claude Code cloud session;
- README, `docs/hosts.md`, `docs/agents/extend.md` and the playbooks say what the code does.

## B23 — Comparative baselines: no Orbit, the 0.4.0 plugin, 0.5.0

**Priority:** P1. Kept apart from B2, because B2 measures one plugin's rates, while B23 compares plugins and needs
arms in the harness.

**Problem.** Nobody knows what Orbit adds or what it costs. 0.4.0's metrics only compare Orbit with itself.

**Scope.**
- **Three arms on the same cases:**
  - `none`, with no plugin;
  - `baseline`, the plugin built from tag `v0.4.0`;
  - `release`.
  Same model, frozen inputs, runner image and limits.
- **Grading.** Hidden checks and owners' records decide the outcome, never Orbit's internal state alone. Selection
  metrics apply only to the two Orbit arms.
- **Reporting.** `metrics --by=arm`, and `orbit_overhead`: the cost, turns and tokens of an arm minus the `none`
  arm's. B2's reliability report carries the comparison.
- **Coverage.** First the activation suite, then B1's workflow cases and B2's held-out fixture once they exist.

**Dependencies.** B22's M4 (the kind and its arms), and B2 (repeats and the report).

**Acceptance criteria.**
- The `none` arm loads no Orbit: no hooks and no trail, tested on the Docker double.
- The baseline arm's manifest names its plugin revision.
- Limits and inputs are identical across the arms.

**Done when:** the reliability report shows, for the activation suite on one release candidate, the pass@1 of each
arm, its cost per verified task and its overhead.

---

## Release criteria for 0.5.0

- Everything 0.4.0 required, on the release commit (ADR 0049).
- The new suites (B1, B3, B4) are present, with every control held. Their model-carried rows are recorded.
- **Promotion rule (proposed):** a recorded model-carried row becomes required in the release after the one in which it
  reached pass@1 ≥ 80% over at least 5 Opus runs.
- The reliability report (B2) is published with the release notes, with B9's tool-call failure rates in it.
- CLAUDE.md "Shipping a release from Claude Code cloud" is updated with what the 0.5.0 ships taught.
- B21's and B22's deterministic rows are required in the fast tier: the catalog and description budget, reachability,
  the routing corpus, the strategy table and the context relevance rules.
- The activation suite (B22) is present with every control held. Proposed, as for B1, B3 and B4: its controls are
  required once it lands. Its model-carried rows are recorded.
- The reliability report carries B23's comparison of the three arms for the activation suite.
- The activation benchmark's KPI targets are recorded. They gate nothing until the owner promotes them.

2. The usage budget per release for repeated runs: how many Opus runs per release candidate the plan can carry.
3. Should 0.5.0 aim for Sonnet on the QA rows, for cheaper releases, or stay on Opus?
4. B1: should a skipped QA step (nothing startable) block workflow completion when the change is user-facing?

7. B22: should a plain change request go DIRECT to `orbit-develop`, or keep entering the coordinated workflow as
   `/orbit-help` does today? A plain request names no autonomy, no verification and no work item. The proposal is
   DIRECT. orbit-help keeps coordinating a task a person hands it either way.
8. B22: should the Stop hold be on by default (proposed), or opt-in?
9. B22: confirm the description budget (at most 300 characters per skill, 7,500 in total) after M0 measures the
   listing. Should any skill be explicit-only (`disable-model-invocation`)? The proposal is none.
10. B22 and B23: what model budget per release can the activation suite use, on top of B2's repeats? The estimate is
    $100 to $200 for a recorded pass and $300 to $600 for a reliability pass.
11. B22: should the activation suite's controls become required for a release when it lands (proposed, as for B1, B3
    and B4)?
12. B22: if the host honours `Bash(<pattern>)` in an agent's `tools:`, should the seven agents whose contract is
    read-only be narrowed to Orbit's own commands? **Answered by M0:** the host does not honour a pattern there
    ([0.5.0-activation-baseline.md](../audit/0.5.0-activation-baseline.md) §2). Narrowing would need a synchronous
    PreToolUse rule on every Bash call, which is deferred.
